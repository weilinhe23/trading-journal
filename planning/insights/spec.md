# 核心经验库功能规格

## 1. 背景

交易系统的每周周报通过 `WeeklyReport.keyLessons` 保存“核心经验教训”。当前数据库已有 24 份周报，且每份周报都填写了核心经验。随着周报增多，用户需要逐周翻阅才能找到过去的经验，也难以识别措辞不同但含义相近的重复经验。

现有月报和季报会按换行拆分 `keyLessons`，再通过整行文本完全匹配识别重复。该方法无法归并以下类型的相似表述：

- “Level 与 K 线结合使用，Level 权重更高”；
- “Level 和 Chart 冲突时优先考虑 Level”；
- “15M K 线用于确认方向，1M 用于优化进入”。

本功能建立一个独立的“经验库”，集中展示、搜索和整理周报中的核心经验。系统自动收集新周报的原始经验，并推荐可能相关的已有经验；用户确认归并结果。

## 2. 目标

本功能实现以下目标：

1. 集中展示所有已整理的核心经验；
2. 支持关键词搜索、标签筛选和来源周回溯；
3. 周报保存后自动收集新填写的核心经验；
4. 通过关键词和标签推荐相似经验，减少重复创建；
5. 允许用户把原始经验归入已有经验、新建经验或明确忽略；
6. 自动计算每条经验出现于多少周，以及最近出现在哪一周；
7. 支持编辑、合并、置顶和归档经验；
8. 保留周报原文，不因经验标题或说明的修改而丢失历史上下文。

## 3. 非目标

本期不实现以下功能：

- 不记录每日是否执行某条经验；
- 不计算经验遵守率；
- 不将经验与交易盈亏、R、MAE 或 MFE 建立验证关系；
- 不实现经验验证状态机或行为实验；
- 不在盘中弹出经验提醒；
- 不使用 AI、向量数据库或语义模型自动合并经验；
- 不自动修改策略内容；
- 不强制用户在保存周报时完成经验整理；
- 不把关键词相似直接视为语义相同。

## 4. 核心定义

### 4.1 规范化经验

规范化经验是用户整理后形成的可复用描述，例如：

> Level 与 K 线方向冲突时，先判断 Level 的重要性，通常提高关键 Level 的权重。

规范化经验可以关联多个来源周。用户可以修改它的标题、说明和标签，但这些修改不覆盖周报原文。

### 4.2 原始经验

原始经验是系统从某份周报的 `keyLessons` 中拆出的单条文本。每条原始经验具有三种整理状态：

- `PENDING`：尚未处理；
- `LINKED`：已经归入一条规范化经验；
- `IGNORED`：用户明确决定不放入经验库。

“待整理”只显示 `PENDING`，不显示 `IGNORED`。

### 4.3 出现次数

出现次数按不同来源周计算。同一经验在同一周关联两条原始文字，仍只计为出现一周。

### 4.4 自动收集与自动归并

系统自动收集周报原文，但不自动决定归并关系。系统可以推荐候选经验，用户负责确认。

## 5. 用户故事

### 查看经验

- 作为用户，我希望在一个页面查看所有已整理经验，不需要逐周打开周报。
- 作为用户，我希望搜索“VWAP”“15M”“Gap”等关键词，找到相关经验和来源原文。
- 作为用户，我希望按标签筛选经验。
- 作为用户，我希望看到一条经验出现于多少周，以及最近出现时间。
- 作为用户，我希望展开经验卡片，查看所有来源周和当时的原文。
- 作为用户，我希望点击来源周，跳转到对应周报。

### 整理新经验

- 作为用户，我保存周报后，希望系统自动识别本周填写的原始经验。
- 作为用户，我希望系统为每条原始经验推荐少量相关候选，减少查找时间。
- 作为用户，我希望一键归入已有经验、创建新经验或忽略该条原文。
- 作为用户，我希望先关闭整理面板，之后从“待整理”继续处理。
- 作为用户，我希望保存周报本身不依赖经验整理是否完成。

### 维护经验库

- 作为用户，我希望修订经验标题、说明和标签。
- 作为用户，我希望把两条重复经验合并，并保留双方的所有来源周。
- 作为用户，我希望置顶经常查阅的经验。
- 作为用户，我希望归档过时经验，并能在归档列表中恢复。

## 6. 数据设计要求

实施方案应至少使用两个数据概念，不把来源周 ID 数组直接存进经验记录。

### 6.1 Insight

建议字段：

- `id: String`：主键，使用 cuid；
- `title: String`：一句话经验；
- `content: String?`：详细说明；
- `tagsJson: String`：JSON 字符串数组，默认 `[]`；
- `status: InsightStatus`：`ACTIVE` 或 `ARCHIVED`；
- `isPinned: Boolean`：是否置顶；
- `createdAt: DateTime`；
- `updatedAt: DateTime`。

说明：当前项目使用 SQLite，Prisma 不支持 SQLite 标量数组；标签可以沿用项目现有 JSON 字符串模式。数据量较小时，服务端可以读取后过滤。若实施研究认为规范化标签表更合适，可以在计划中说明理由。

### 6.2 InsightSource

建议字段：

- `id: String`：主键，使用 cuid；
- `weekStart: DateTime`：关联 `WeeklyReport.weekStart`；
- `sourceText: String`：周报原文快照；
- `normalizedText: String`：用于幂等同步和候选匹配的规范化文本；
- `sourceHash: String`：用于识别同一周的同一原始经验；
- `sortOrder: Int`：在周报中的显示顺序；
- `state: InsightSourceState`：`PENDING`、`LINKED` 或 `IGNORED`；
- `insightId: String?`：关联的规范化经验；
- `createdAt: DateTime`；
- `updatedAt: DateTime`。

关系约束：

- 删除或归档 Insight 时不得丢失来源原文；
- 合并 Insight 时，把来源记录迁移到保留的 Insight；
- `LINKED` 状态必须存在 `insightId`；
- `PENDING` 和 `IGNORED` 不应关联 Insight；
- 同一周、同一规范化原文不得因重复保存而产生重复来源记录。

### 6.3 派生字段

以下字段从 `InsightSource` 实时计算，不写入 `Insight`：

- `occurrenceCount`：关联来源覆盖的不同周数；
- `lastSeen`：关联来源中的最大 `weekStart`；
- `sourceCount`：关联原始文本数量。

## 7. 原始经验拆分规则

现有 `keyLessons` 是自由文本，常见格式包括：

- 每行一条；
- `1.`、`2.` 编号；
- `1、`、`2、` 中文顿号编号；
- 空行分隔；
- 单段、无编号文本。

系统应先规范换行和空白，再按明确的换行或编号边界拆分。系统不得仅按句号拆分，因为一条经验可能包含多句解释。

周报保存后的整理面板应显示拆分预览。用户可以在归并前：

- 修改某条原始文本；
- 把一条拆成两条；
- 把相邻两条合并。

实施方案必须定义幂等同步策略，满足：

- 重复保存未修改的周报不会产生重复来源；
- 修改周报会创建或更新相应待整理来源；
- 删除尚未整理的原文会删除对应 `PENDING` 来源；
- 已经 `LINKED` 或 `IGNORED` 的历史来源不会被静默删除；
- 已整理来源与当前周报文字不一致时，系统保留原始快照并提供明确处理方式，不静默覆盖历史。

## 8. 周报保存与整理流程

### 8.1 保存

用户点击“保存周报”后：

1. 系统先保存 `WeeklyReport`；
2. 保存成功后同步 `keyLessons` 到 `InsightSource`；
3. 周报保存结果不受后续整理操作影响；
4. 如果存在新的 `PENDING` 来源，页面显示“整理本周经验”入口并标注数量；
5. 系统可以自动打开侧边面板，但用户可以直接关闭。

### 8.2 整理面板

面板逐条展示本周 `PENDING` 来源。每条提供：

- 原始文字；
- 自动提取的关键词标签；
- 最多 3–5 条推荐候选；
- 搜索全部已有经验；
- “归入已有经验”；
- “新建经验”；
- “忽略”；
- 拆分或合并原始条目。

新建经验时：

- 默认用原始文字预填标题；
- 用户可以缩短标题并填写说明；
- 系统推荐标签，用户可以增删；
- 保存后自动把来源状态设为 `LINKED`。

### 8.3 候选推荐

MVP 使用确定性规则，不使用 AI：

- 英文关键词不区分大小写；
- 识别项目常用词，如 `Level`、`15M`、`5M`、`1M`、`VWAP`、`Gap`、`PMH`、`PML`、`PDH`、`PDL`、入场、退出、趋势、震荡、新闻、耐心、纪律；
- 比较标题、说明和标签的关键词重合；
- 优先显示最近出现或置顶的候选；
- 关键词相似只提供推荐，不自动提交归并。

实施计划应把匹配逻辑放在可测试的服务端或共享工具函数中，不把规则散落在 React 组件里。

## 9. 经验库页面

新增路由 `/insights`，页面名称为“经验库”。MVP 可以先在周报列表和周报详情页提供入口；是否加入顶层导航由实施计划根据现有导航密度决定。

### 9.1 顶部工具栏

- 全文搜索框；
- 标签筛选；
- 状态筛选；
- 排序选项：最近出现、出现最多、最近编辑；
- “待整理 N 条”入口；
- “新建经验”按钮。

搜索范围至少包括：

- Insight 标题；
- Insight 说明；
- Insight 标签；
- 关联的来源原文。

### 9.2 视图

至少提供：

- “全部经验”：默认显示 `ACTIVE`；
- “待整理”：显示所有 `PENDING` 来源；
- “已归档”：显示 `ARCHIVED`；
- “已忽略”：可选的次级视图，用于恢复误操作。

### 9.3 经验卡片

每张卡片显示：

- 标题；
- 说明摘要；
- 标签；
- 出现周数；
- 最近出现日期；
- 置顶状态；
- 编辑、合并和归档操作。

展开后显示：

- 按时间倒序排列的来源周；
- 每周原始文字；
- 跳转到 `/weekly/[weekStart]` 的链接。

默认排序建议：置顶优先，其余按最近出现时间倒序。

### 9.4 合并经验

用户从某条经验发起合并：

1. 选择目标经验；
2. 预览双方标题、说明、标签和来源数量；
3. 选择保留的标题和说明；
4. 标签取并集，用户可调整；
5. 把被合并经验的来源迁移到目标经验；
6. 归档或删除空的被合并记录；
7. 整个操作在数据库事务中完成。

## 10. 最近高频主题提示

在周报“核心经验教训”输入区域旁，可以增加一个非阻塞提示：最近 8–12 周最常出现的三个主题。

计算规则：

1. 查询时间窗口内的 `LINKED` 来源；
2. 按关联 Insight 或标签统计不同来源周数；
3. 按近期出现周数排序；
4. 不使用 Insight 的历史总次数代替近期次数；
5. 点击主题可打开经验详情或经验库筛选结果。

该提示属于加分项。实施计划可以把它放在核心 MVP 之后。

## 11. API 范围

实施计划应设计符合现有 Next.js App Router 风格的 API。建议覆盖：

- Insight 列表、创建、读取和更新；
- Insight 归档与恢复；
- Insight 合并；
- InsightSource 列表；
- InsightSource 归入已有经验；
- InsightSource 创建新经验并关联；
- InsightSource 忽略与恢复；
- 指定周报的核心经验同步；
- 历史周报批量回填。

所有写接口必须使用 Zod 或项目现有的等价校验方式校验输入。合并、多记录迁移和状态变更应使用 Prisma 事务。

## 12. 历史数据回填

首次上线需要处理现有周报：

1. 读取所有非空的 `WeeklyReport.keyLessons`；
2. 按同一拆分规则生成 `InsightSource`；
3. 全部初始状态设为 `PENDING`；
4. 脚本或内部接口可以重复运行，重复运行不得生成重复数据；
5. 回填不修改 `WeeklyReport.keyLessons`；
6. 回填前后输出周报数、原始条目数和跳过数；
7. 回填失败不得破坏现有周报数据。

历史回填后，用户可以在“待整理”页面分批归并，不要求一次整理完成。

## 13. 与现有月报和季报的关系

MVP 保留现有月报和季报页面，避免扩大首期范围。实施计划应说明两种汇总口径暂时并存的影响。

后续阶段可以把月报和季报的“重复教训追踪”改为读取 `InsightSource`：

- 使用已归并经验识别语义相同的重复内容；
- 保留未整理条目的提示；
- 删除当前按整行文本完全匹配的重复逻辑。

该替换可以作为第二阶段，不阻塞经验库 MVP 上线。

## 14. 非功能要求

- 所有日期继续遵守项目的 ET 和 `YYYY-MM-DD` 规范；
- 数据保存在本地 SQLite；
- 不引入新的云服务；
- 不安装 AI、向量搜索或全文搜索服务；
- 优先使用现有 shadcn/ui 和 Tailwind CSS；
- 经验整理不得阻断周报保存；
- 页面应适配现有深色主题；
- 数据量较小时优先选择简单、可测试的实现；
- 所有 Prisma Schema 修改后必须运行 `pnpm db:push`；
- 不修改 `src/components/ui` 下的基础组件。

## 15. 错误处理

- 周报保存成功、经验同步失败时，保留周报保存结果，并提示“周报已保存，经验同步失败，可重试”；
- 归并失败时，不改变来源状态；
- 合并 Insight 失败时，事务必须回滚；
- 无效或不存在的 `weekStart`、Insight ID 和 Source ID 返回明确错误；
- 重复请求必须保持幂等，不产生重复来源或重复关联；
- 用户关闭整理面板不会丢失 `PENDING` 来源。

## 16. 测试范围

实施计划至少覆盖以下测试：

### 单元测试

- 核心经验拆分；
- 文本规范化和哈希；
- 关键词及标签提取；
- 候选排序；
- 不同周数和最近出现时间计算。

### API 测试

- 周报同步幂等；
- 归入已有经验；
- 新建经验并关联；
- 忽略和恢复；
- 合并经验事务；
- 归档和恢复；
- 无效输入与不存在记录。

### 页面测试

- 搜索和标签筛选；
- 三种排序；
- 展开来源并跳转周报；
- 待整理面板的三个处理动作；
- 保存周报后出现待整理数量；
- 经验同步失败不影响周报保存结果。

### 回填验证

- 现有非空周报均能生成来源；
- 重复运行回填后记录数量不变；
- 原 `keyLessons` 内容保持不变。

## 17. MVP 验收标准

满足以下条件即可验收 MVP：

1. `/insights` 可以查看、搜索和筛选规范化经验；
2. 每张经验卡显示不同来源周数和最近出现时间；
3. 用户可以展开原文并跳转到来源周报；
4. 新周报保存后自动生成待整理原始经验；
5. 重复保存同一周报不会生成重复来源；
6. 用户可以归入已有经验、新建经验或忽略；
7. 用户可以稍后从“待整理”继续处理；
8. 用户可以编辑、置顶、归档和合并经验；
9. 合并后所有来源仍可访问，统计结果正确；
10. 历史周报可以安全、幂等地回填；
11. 周报保存与经验整理相互解耦；
12. `pnpm typecheck` 和项目适用的检查命令通过。

## 18. 实施规划需要回答的问题

后续实施方案应明确：

1. 需要新增和修改哪些 Prisma 模型、枚举和索引；
2. 如何让周报编辑后的来源同步保持幂等；
3. 历史回填采用脚本、内部 API 还是一次性迁移；
4. API 路由及其请求、响应结构；
5. 服务端查询如何计算来源周数、最近出现和全文搜索；
6. 页面应拆成哪些服务端组件和客户端组件；
7. 候选匹配逻辑放在哪个模块，如何测试；
8. Insight 合并如何使用事务并处理重复来源；
9. 如何在不阻断周报保存的情况下报告同步失败；
10. 是否在 MVP 中加入顶层导航和最近高频主题提示；
11. 分阶段实施顺序、每阶段验收条件和回滚方式；
12. 哪些现有月报、季报逻辑应立即复用，哪些留到第二阶段。
